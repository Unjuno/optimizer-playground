# 詳細仕様案

状態：要件整理 v0.1。実装前。決定・提案・未決の区別は [設計の決定事項](../DESIGN-BASELINE.md) を参照。

## 1. 目的と非目標

### 目的

利用者が独自のオプティマイザを作り、人工的な損失地形上で実行し、軌跡・状態・評価履歴から挙動を理解し、必要に応じて結果を共有できること。

関連する設計領域は、数値最適化、科学的可視化、人間とコンピュータの相互作用、実行環境のセキュリティである。初期版では、最適化規則の自由度と、理解しやすく再実行できる実験を両立させる。

### 非目標案

初期版では、機械学習性能の一般的な優劣の判定、大規模モデル学習、サーバー側の計算代行、利用者向けの追加実行ソフト、個人アカウント、個人用クラウド保存、オプティマイザの自動発明、任意Python/CUDA環境との無変更互換を要件にしない。

## 2. 中心となる体験

利用者は損失地形を選択・編集し、開始点と予算を指定し、既存例または自作オプティマイザを実行する。画面上で移動経路と履歴を見ながら変更し、同じ条件で比較する。公開を選択した場合のみ投稿内容を確認して送信する。

画面の細かな配置は未決定。必要な役割は、地形編集、オプティマイザ編集、実験制御、可視化・解析、投稿確認、共有閲覧である。これらを何画面に分けるかは実装前のUI設計で決める。

## 3. 損失地形

### 初期対象案

2変数の実数値目的関数を扱う。等高線上の位置が最適化対象の2変数、地形の高さが目的関数値に対応する。高さ付き3D表示は追加候補とし、2Dの等高線だけでも中核操作を完結させる。

実装開始時の基準問題は単純な凸の地形とし、比較用に細長い谷、曲がった谷、複数の谷、平坦部や鞍点を含む例を追加する案とする。個別問題の式・範囲・既知の最適値・停止基準は別途定義してバージョンを固定する。

### 編集方法

プリセット、数式入力、手描きを対象とする。手描きは高さを持つ地形を編集する方式とし、補間・平滑化・微分の方法を実装仕様として明記する。グラフ上の見た目だけを変えて、評価対象が変わらない実装にはしない。

損失地形を基準に勾配を求める設計を提案する。独立に描いた任意のベクトル場を、そのまま同じ「損失関数の勾配」と呼ぶ仕様にはしない。ベクトル場そのものの実験は必要なら別モードにする。

定義域外、数値を返さない入力、非有限値、微分できない点、境界での振る舞いを定義する。範囲外の値を黙って切り詰めたり、勾配を自動的に別物へ置き換えたりしない。

### 実行中の地形変更

比較モードでは実行開始時の地形を固定する。地形を編集した場合は、新しい実験として開始することを基本案とする。

動かしながら地形を変形するモードは将来候補とし、導入する場合は「時間とともに目的が変わる探索」と表示し、固定問題の比較結果に混ぜない。

## 4. オプティマイザの作成

### 自由度

既存手法の選択だけでなく、独自の状態管理、条件分岐、行列演算、複数の候補点、複数回の関数評価などを記述する余地を残す。状態の本数や演算数を、過去の提案にあった2本・7種類へ固定しない。

ただし、対象は選定したランタイムが扱えるプログラムであり、実行資源と評価タスクの対応能力には上限を設ける。使用可能な言語・標準ライブラリ・演算・数値精度・非対応項目を明示する。

### コードと視覚編集

実行されるコードを基準とし、ノードや数式から編集できる範囲を宣言する。非対応部分はカスタムコードとして保持する。コードの変更を反映できない場合は、古いノード表示を現行コードと同等に見せない。

未対応コードを黙って削除・簡略化・置換しない。可視化できない処理でも、実行の入出力仕様を満たせばコードとして評価できる設計を目指す。

### 評価タスクとの接続要件案

以下は機能上の契約であり、関数名や型定義は未確定である。

| 機能 | 要件案 |
|---|---|
| 初期化 | 設定と開始条件から任意の内部状態を構築できる |
| 目的関数評価 | 指定した点または点群を評価する。回数を実行側で記録する |
| 勾配評価 | 対応タスクが提供する。利用回数と実装方式を記録する |
| 追加の微分情報 | 対応可否を宣言する。未対応を無言で近似処理に置き換えない |
| 反復の進行 | 1回の進捗報告までに複数の評価を行う実装を許容する |
| 状態 | 任意の内部状態を許容し、公開・再現用に保存できる範囲を別途定義する |
| 観測値 | 代表点、点群、更新方向、名前付きの内部統計などを報告できる |
| 終了 | 正常終了、予算終了、異常、利用者による停止を区別する |
| 対応能力 | 必要な評価機能とデータ型等を実行前に検査する |

外側の「1更新」を、関数評価1回と同義にしない。勾配不要手法を評価する場合は、勾配の利用を必須条件にしない。複数点を扱う場合も、単一の経路だけを正しい出力とみなさない。

オプティマイザの内部状態表示は選択式とし、巨大な配列全体の描画を常に要求しない。

## 5. ブラウザ実行

最適化の計算は利用者の端末内で実行する。ページの操作と計算を分け、停止操作・予算超過・エラーを表示できる構成を目指す。

最初の検証目標はCPUで中核機能を動作させることとし、GPUは選定したバックエンドと実機で対応を確認してから追加する案とする。CPUとGPU、異なるブラウザ間のビット単位の一致を、検証なしに保証しない。

GPUを使えない場合のCPU実行、対応外の表示、バックエンド選択の挙動を定義する。対応ブラウザ、数値型、乱数生成方法、ランタイムのバージョンを実行記録に含める。

実行時間、関数評価回数、勾配評価回数、点群サイズ、状態・履歴・描画データ量などに上限を設定する。値は未決定であり、実機試験で決める。

## 6. 可視化

必須候補は、等高線、開始点・現在位置、更新軌跡、勾配方向、実際の更新方向、目的関数値の履歴、停止理由とする。複数手法は識別可能な線・記号で比較する。

再生、一時停止、再開、1更新送り、リセット、強制停止を提供する。強制停止と再開可能な一時停止は別の操作・状態として扱う。

計算結果の記録とアニメーションの表示速度を分ける。再生を速くしたり遅くしたりしても、同じ実験ログの数値結果は変化しない設計とする。

勾配の描画に追加計算が必要な場合は、オプティマイザが利用した評価と診断・描画用の評価を分けて記録する。視覚化が無計上の探索情報にならないよう、実行側と表示側の経路を分離する。

## 7. 比較と評価

### 二つのモード

自由実験モードでは地形・開始位置・設定を編集する。比較モードでは問題のバージョン、開始条件、seed、評価予算、計算条件を固定する。両者の結果を同じ条件の成果として混同しない。

### 記録項目

| 分類 | 記録内容 |
|---|---|
| 問題 | 地形の定義とバージョン、範囲、開始条件、利用可能な評価機能 |
| 実装 | オプティマイザコード、コード版、設定、状態初期化方法 |
| 実行条件 | seed、ランタイム、バックエンド、数値型、評価予算、計測方法 |
| 結果 | 目的関数値の履歴、最終値、観測された最良値、最終位置 |
| 費用 | 関数・勾配・追加微分情報の評価回数、更新回数、計算時間 |
| 終了 | 目標到達、予算到達、数値異常、実行エラー、手動停止 |
| 公開状態 | 本人の端末による未検証の結果か、別環境で再実行された結果か |

「目標到達」は問題ごとに明示した閾値に対して判定する。任意に手描きされた問題について、既知でない大域最適解への到達を断定しない。最終値と観測最良値を別々に示す。

単一の曲線だけで優劣を決めず、複数の開始点・seedで確認できる設計にする。手法ごとにパラメータ調整をした場合は、その調整予算と選択方法も記録する。

異なる端末の壁時計時間を、そのまま公平な総合順位にしない。評価回数も演算の総費用そのものとは同一視せず、複数の指標を並記する。計算時間と描画・アニメーション時間は分離する。

正確なメモリ使用量を取得できない環境では、取得不能と表示するか、何を数えた推定値なのかを明記する。計測していない値を埋めない。

## 8. 個人用保存と投稿

### 投稿前

実験はブラウザ内の一時状態として扱い、個人用保存・非公開クラウド保存・下書きの自動永続保存は初期版に設けない案とする。再読み込みやタブ終了で未投稿の作業が失われることを表示する。

共有しないコード、地形、実行ログを自動的にアップロードしない。アクセス記録など運用上のデータと、実験内容の送信は区別し、収集方針を別途定義する。

### 投稿時

送信するコード、地形、条件、履歴、環境情報の範囲を利用者へ表示し、明示的な操作で送信する。秘密情報や個人情報の混入を避ける注意表示を設ける。投稿内容は必要な範囲に限定する。

公開後に他者が再実行できるよう、再現に必要な設定とバージョンを含める。すべての結果が同じ値になる保証はせず、再実行時の環境差を表示する。

### 共有URL

投稿を識別するURLを発行する。公開一覧・検索・ランキングを初期版に設けない案とする。URLを知っている人が閲覧できる公開投稿として説明し、アクセス制御された秘密文書という位置付けにはしない。

共有ページを開いただけで第三者のコードを自動実行しない。内容を閲覧した後、明示的な実行操作を要求する。

### 削除キー

投稿ごとに削除用の秘密キーを発行し、共有URLとは分けて扱う。秘密キーを共有ページ、公開リポジトリ、通常の運用ログへ含めない。

提案：サーバーには秘密キーの平文を保存せず、照合用の値を保存する。生成・送信・照合・試行回数制限の仕様はセキュリティ設計で確定する。

キーを紛失したときの本人向けの復旧機能は初期版に設けない案とする。運営側の通報対応・不適切投稿の削除は、利用者のキー削除とは別に定義する。

削除対象は運営管理下の投稿本文・添付結果とする。キャッシュやバックアップの削除時期は運用方針で定義する。外部サイトや閲覧者によるコピーの消去は保証の対象にしない。

## 9. 任意コードを公開実行する際の公開条件

以下は達成すべき要件であって、現在安全に実現できているという主張ではない。

未信頼コードが、アプリの画面、投稿・削除の権限、秘密キー、他の実験、不要なネットワーク通信へ直接アクセスできないようにする。計算を別処理に分けるだけで満足せず、権限分離と資源制限を独立に検証する。

目的関数の数式、手描きデータ、投稿メタデータも未信頼入力として扱う。評価ログの形式、データ量、表示内容を検査する。

無限ループ、非常に大きな確保要求、大量のログ、非有限値、例外、通信の試行、削除権限へのアクセス、投稿の連投などを試験対象とする。資源制限・隔離を確認できるまでは、任意投稿コードを一般利用者向けに実行させない。

実行停止ができることと、安全な権限境界を持つことは別の検証項目にする。

## 10. 受け入れ基準案

| 領域 | 確認すること |
|---|---|
| 基本実行 | 既定の地形と開始点から、参照実装と許容誤差内で一致する更新履歴が得られる |
| 編集 | コードと対応する視覚編集の変更が実行へ反映され、非対応コードが保持される |
| 観察 | 勾配方向と実更新方向を区別し、再生速度を変えても数値ログが変わらない |
| 評価 | 関数評価・勾配評価・描画用評価の回数を識別できる |
| 異常系 | 非有限値、例外、予算超過、強制停止を誤った成功として表示しない |
| プライバシー | 投稿操作前に実験内容が外部へ送信されない |
| 共有 | 投稿を別セッションで閲覧でき、自動実行されず、再実行条件が読み出せる |
| 削除 | 正しいキーで対象投稿を削除でき、誤ったキーでは削除できない |
| 互換性 | 対応環境・非対応環境を識別し、未検証環境の結果を保証しない |

### H / T / D / C / U

**H（検証仮説）**：指定した対応環境において、コード編集から実行・観察・比較・任意共有までが、定義した入出力と予算に従って動く。

**T（最小検証案）**：単純な凸問題、細長い谷、非凸問題の3種類、各3開始点、基準実装2種類で計18条件を確認する。乱数を使う実装は各条件3 seedを最低限の動作確認案とする。これは性能優劣を統計的に主張するための必要標本数ではない。停止条件は予算到達・数値異常・例外・手動停止とし、実験後に都合よく変えない。

**D（判定案）**：定義した参照値・許容誤差・全受け入れ項目を満たしたものをPASS、逸脱をFAIL、未実行・非対応・計測不能をUNCERTAINとして記録する。許容誤差と予算の具体値は、数値型と実装方式の決定後、試験実施前に固定する。

**C（対立説明・破れ方）**：軌跡の見かけ上の改善が描画の違いだけで生じる、開始点の選び方に依存する、評価回数の漏れで有利になる、地形を変えた結果を同一問題として扱う、端末性能差をアルゴリズム性能差と誤認する。

**U（不確かさ）**：丸め、補間・微分方式、乱数、バックエンド、端末負荷、描画の影響を分けて記録する。測定をまだ行っていないため、合成標準不確かさと包含係数は算出しない。推測の数値をベンチマークとして掲載しない。

## 11. 未検証事項

文書作成時点で、アプリの実装、実機の動作確認、GPU対応、隔離方式の安全性、性能測定は完了していない。公開リポジトリでの調整により、技術選定と具体的な仕様を確定する。
